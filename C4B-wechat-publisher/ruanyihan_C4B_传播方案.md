# 传播方案 — 文章发布与效果追踪设计

> 挑战：C4B 公众号文章生成技能 ｜ 提交人：阮依涵
> 目标：不只「发出去」，而是**发出后有人看、有人用、有数据可复盘**。

---

## 一、传播目标（可量化）

| 层级 | 目标 | 衡量指标 |
|------|------|---------|
| 触达 | 让群内同学看到这篇文章 | 阅读量 ≥ 100 |
| 认同 | 读者觉得方法可用 | 点赞 ≥ 15，在看 ≥ 8 |
| 传播 | 有人愿意转给别人 | 转发 ≥ 5 |
| 行动 | 有人真的去用/装这个技能 | 群内询问 ≥ 3 人次 / 仓库 star ≥ 5 |

> 定这样的目标是因为：**「发布即弃」是本次 rubric 明确列出的扣分信号。**
> 所以传播方案的重点不是渠道数量，而是「有没有闭环」。

---

## 二、渠道设计（4 条，按优先级排序）

### 渠道 1：公众号首发（主阵地）

| 项目 | 内容 |
|------|------|
| 平台 | 微信公众号（订阅号） |
| 发布时间 | 工作日 **晚上 20:00–22:00**（微信阅读高峰） |
| 内容 | 《一个人 + 一个 AI = 一个内容工厂》全文 |
| 关键动作 | 文末引导「在看 + 转发」；置顶留言放技能获取方式 |
| 为什么 | 这是唯一能沉淀「阅读—点赞—在看—转发」完整数据的渠道 |

### 渠道 2：Elite20 挑战群 / 学习群（精准触达）

| 项目 | 内容 |
|------|------|
| 形式 | 发文章链接 + 一句「我做了什么」 + 一张运行截图 |
| 时机 | 文章发布后 **10 分钟内**（公众号初始推荐权重看首小时数据） |
| 关键动作 | 主动邀请群友「拿我的技能试一篇你的文章」 |
| 为什么 | 群友是**最可能真的去用**的人，能带来最有效的反馈 |

**群内推广话术（可直接复制）：**

> 分享一个我这周做的小工具：把 Markdown 直接转成公众号排版好的 HTML，一条命令搞定。
>
> 之前写公众号最烦的就是排版——调字号、对齐、修图片，一篇文章要花 40 分钟在这些重复劳动上。
> 现在写完 Markdown，跑一条命令，复制粘贴就完事。
>
> 顺手把过程里踩的 6 个坑也写进文章了（比如一个 emoji 就能让脚本在 Windows 上崩溃 😅）。
> 有兴趣的同学可以拿自己的文章试试，装了直接跑，有问题群里问我。
>
> 👉 [文章链接]

### 渠道 3：朋友圈（扩散层）

| 项目 | 内容 |
|------|------|
| 形式 | 文章卡片 + 一段「解决了什么真实痛点」的自述 |
| 关键动作 | 附一张**预览页截图**（视觉冲击 > 文字描述） |
| 为什么 | 朋友圈的转化靠「图好看 + 痛点准」，而不是靠文采 |

### 渠道 4：GitHub 仓库（沉淀层）

| 项目 | 内容 |
|------|------|
| 形式 | 把技能源码 + README + 示例推到公开仓库 |
| 关键动作 | README 里放「三步上手」，降低别人试用的门槛 |
| 为什么 | 公众号文章会被刷走，**仓库是长期资产**；也是「可复用性」的直接证明 |

## 四、互动设计（提升互动的具体动作）

| 动作 | 具体做法 | 目的 |
|------|---------|------|
| **文末提问** | 结尾问「你最想让 AI 帮你自动化掉哪件重复的事？」 | 降低留言门槛，几乎人人都有答案 |
| **置顶留言** | 自己的留言置顶：「技能获取方式 + 有问题直接问我」 | 把读者从「看」推向「用」 |
| **留言必回** | 发布后 24 小时内回复全部留言 | 提升账号互动权重，也给读者正反馈 |
| **征集案例** | 「用我的技能发了文章的同学，我把你的链接放到 v2 的案例区」 | 把使用者变成传播者 |
| **揭晓踩坑** | 文章里列的 6 个坑，在群里陆续展开讲 2–3 个的细节 | 制造持续话题，而不是一次性发布 |

## 五、发布节奏与检查清单

### 发布前（T-30min）

- [ ] 预览页逐屏检查：标题、目录、Callout、表格、代码块、公式、页脚
- [ ] 手机预览模式检查（公众号后台可切手机预览）
- [ ] 确认无缺图（base64 已自动转存素材库）
- [ ] 准备封面图
- [ ] 写好群内推广话术、朋友圈文案（提前写好，避免临场想词）

### 发布时（T+0）

- [ ] 发布文章
- [ ] 立即自查：打开文章链接确认排版无异常
- [ ] 群内分享（10 分钟内）
- [ ] 朋友圈分享

### 发布后（T+1h ~ T+72h）

- [ ] T+1h：记录首次数据
- [ ] T+24h：回复全部留言、记录数据
- [ ] T+72h：记录数据、统计渠道贡献、整理同学反馈
- [ ] 把反馈整理成 v2 需求清单（对应 AAR 第 6 节）

## 六、风险与预案

| 风险 | 预案 |
|------|------|
| 粘贴后排版错位 | 已用 `--validate` 预检；发布前务必手机预览 |
| 图片丢失 | 本地图片已自动 base64 内嵌；发布前扫一遍图 |
| 没有人留言 | 靠自己置顶留言 + 群内定向邀请 2–3 位同学提问，把评论区「点亮」 |
| 阅读量低 | 首小时是关键：群内 + 朋友圈双渠道同步发，集中在一个时间窗 |
| 同学装不上环境 | 提前准备好「一条命令装依赖」的说明，有问题即时在群里答疑 |

---

## 七、为什么这个方案是「合理」的

1. **渠道与内容匹配**：技术教程类内容，精准社群（渠道 2）的转化率远高于泛流量。
2. **有数据追踪**：设定了明确的指标、采样时间点和回填表格，不是发完就算。
3. **有互动设计**：文末提问、置顶留言、留言必回、征集案例 —— 四个动作层层递进。
4. **有行动转化记录**：单列一栏记录「有几个人真的用起来了」，
   因为这正是 C4B 想验证的东西。
5. **有闭环**：发布后的反馈会进入 v2 需求清单，形成「发布 → 反馈 → 迭代」的循环。
