你有没有算过这样一个账：写一篇 2000 字的公众号文章，真正「写」的时间可能只有 40 分钟，而排版、调字号、对齐、修图片，能再吃掉 40 分钟。

更糟的是，这 40 分钟是纯重复劳动。每一篇文章都要重来一遍：把标题调成 20 号、把正文行高改成 1.75、给引用加一条竖线、把头图重新上传一次。

我一直觉得这件事不对劲。能被复制的能力，才是真正值钱的能力——既然排版规则是固定的，为什么不让机器去做？

所以我做了这个技能：wechat-publisher-pro。
问题的本质：公众号编辑器是个「挑剔的打印机」

先说清楚为什么这件事不是「随便贴一下」那么简单。

微信公众号编辑器有一套非常严格的 HTML 规则，它不是浏览器，更像一台挑剔的打印机：

| 你在别处的写法 | 公众号编辑器里会发生什么 |
|---|---|
| <h1> 一级标题 | 被禁用，必须降级成 <h2> |
| <div> 布局容器 | 不被可靠渲染，要换成 <p> |
| <style> / class | 全部剥离，样式只能写在行内 |
| 外部链接的图片 | 保存时可能丢失，必须走素材库 |
| SVG 图形 | 保存瞬间消失，只有 PNG 能活下来 |

换句话说：你从 Word 或网页复制过去的东西，有一半会「掉」。 这就是为什么大家宁愿在公众号编辑器里手打一遍——不是不想省事，是省不了。
[!NOTE] 核心结论
排版的痛点不是「不美观」，而是规则不可预测。只要把规则固化成代码，重复劳动就变成了一次性投入。
我做了什么：把规则写成一个技能

这次挑战给了我一份 starter kit（一份基础转换脚本），它已经能处理 Markdown 到 HTML 的转换和基础过滤。但它是「通用工具」——没有主题、没有目录、没有高亮框。

我没有从零开始写。我做的是理解它 → 拆解它 → 改造它。

具体新增了这些能力：

| 能力 | 说明 | 解决什么 |
|---|---|---|
| 主题系统 | 5 套配色方案一键切换 | 让文章有自己的视觉标识 |
| Callout 高亮框 | > [!NOTE] 语法渲染成带色块 | 公众号最核心的排版元素 |
| 自动目录 | 从标题自动生成 | 长文可读性 |
| 文章元数据 | 标题 / 作者 / 日期 / 摘要 | 文章结构完整 |
| 中英文间距 | 自动插入细间距（盘古之白） | 中文排版的专业感 |

| 批量 + 多格式 | 一次导出公众号 / 知乎 / 纯文本 | 一次写作，多平台分发 |

一段话概括它的价值：同一份 Markdown，改一个参数，就是另一种风格。

六个真实的坑，和它们教会我的事

如果你看到这里，觉得「用 AI 写个脚本不就完了」——那下面这部分才是这篇文章真正的价值。

这六个问题，全是我在实际运行中撞出来的。
[!WARNING] 坑 1：emoji 让脚本在 Windows 上直接崩溃
原版脚本用 print("📖 Reading...") 输出日志。听起来无害，但在中文 Windows 的控制台上，终端编码是 GBK，输出 emoji 会直接抛 UnicodeEncodeError 并终止程序。一个表情符号，让整条流水线跑不起来。
修复：启动时把标准输出强制重定向为 UTF-8，并给日志加兜底。
[!WARNING] 坑 2：引用块里的尖括号标记，被正则「吃掉」了
我自定义了 [!NOTE] 这样的高亮框语法。第一版实现是解析完 Markdown 后再从引用块里识别标记，结果 > [!NOTE] 标题 和正文被 Markdown 合并进了同一个段落，标题和正文粘成一坨，怎么都拆不开。
修复：把识别动作提前到 Markdown 解析之前，逐行扫描，天然保留「标记行 / 正文行」的边界。
[!WARNING] 坑 3：拼接 HTML 时，套出了「页面里的页面」
我用字符串拼高亮框内容，再交给解析器塞进段落。结果是 <p> 里面套了一整个 <html><body>——因为解析器默认补全文档结构。
修复：不再用字符串当中间层，改成直接搬运 DOM 节点，结构天然正确。
[!WARNING] 坑 4：--- 分隔符，在输出里凭空消失了
Markdown 的 --- 会生成 <hr>，但 <hr> 不在公众号白名单里，被清洗阶段静默丢弃。不只是丢，而且没有任何提示——你只能靠肉眼发现。
修复：把 <hr> 主动转成一个居中的圆点分隔符，符合公众号审美。
[!WARNING] 坑 5：加粗的「嵌套内容」被拍平了
原版用 get_text() 提取加粗文本，再包一层 <span>。问题是 get_text() 只取文字——如果加粗里还嵌了代码或链接，里面的格式会被一起拍平。
修复：改成搬运子节点，保留内部所有嵌套格式。
[!WARNING] 坑 6：一开始我的自检用例，自己就是错的
我写了一套自检用例来验证技能。第一次跑，3 项失败。排查后发现：不是技能错了，是我的测试样例写错了——我用来测「中英文间距」的句子里，中英文之间本来就有空格，根本没有触发条件。
修复：改用一个真正的「无空格混排」样例，测试才有效。
[!IMPORTANT] 这六个坑的共同点
它们全都不是「AI 不会写代码」，而是「真实环境和你想象的不一样」。emoji 在 Windows 上会崩、解析器会自作主张补全结构、清洗规则会静默吞掉内容。
这些问题不会在纸面上出现，只会在一行行真跑起来的时候出现。
一个公式：为什么「技能化」值得做

如果把一件事的「价值」拆开看：

$$V = n \times q - c$$

其中 $n$ 是覆盖人数，$q$ 是单次质量提升，$c$ 是一次性的建设成本。

传统做法里，$c$ 会随着每篇文章重新付出一次。而一旦把它做成技能，$c$ 只付一次，之后每写一篇，$n$ 和 $q$ 都在累积，成本却是零。

这就是为什么我更愿意花三小时做一个技能，而不是用三十分钟手动排一篇文章。
[!PRACTICE] 你现在就可以做的三件事
1. 翻一翻你最近一周重复做过三次以上的事
2. 问自己：它能不能被描述成「输入 X → 输出 Y」
3. 如果能，就把它交给 AI 去实现，你负责定义规则和验收结果
写在最后

这次挑战里，我最大的收获不是「做出了一个能用的技能」，而是理解了一件事：

在 AI 时代，你不需要自己写每一行代码，但你必须自己定义「什么是对的」。

AI 可以十分钟写出 500 行脚本，但它不知道 emoji 会在你的终端上崩，不知道清洗规则会静默吞掉 <hr>，也不知道你的测试样例本身是错的。这些只有真正跑起来、真正在意结果的人才会发现。

技能会失败，但失败会留下经验。下一次，我会做得更快。

如果你也在写公众号，欢迎试试这个技能。用得越狠，它进化得越快。
[!QUOTE] 一句话总结
一个人 + 一个 AI + 一个排版技能 = 一个完整的内容工厂。你负责想，机器负责排。
