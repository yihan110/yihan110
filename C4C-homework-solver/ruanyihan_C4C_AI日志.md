## 迭代过程

### 轮次 1：理解 Claude 基线（学习）
- **任务**：读懂 starter kit 的架构与接口约定。
- **AI 用法**：通读 `SKILL.md`、`pipeline.py`、`solve.py`、`parse_problems.py`、`render_latex.py`，梳理 5 阶段流水线、problem/solution 数据结构、`SOLVERS` 路由机制。
- **产出**：确认"求解率 = 领域覆盖度"，扩展学科要新增领域知识 + 求解器。
- **经验**：先理解再动手，不盲目照搬。

### 轮次 2：环境探查与选型（规划）
- **任务**：确认本机能力、选定国产模型与学科。
- **AI 用法**：探查 LaTeX（已装 TeX Live 2026）、Python 依赖；实测 DeepSeek API key（调用 `deepseek-chat` 返回正确结果）。
- **决策**：迁移引擎 = DeepSeek（国产、有 key、国内直连）；扩展学科 = 高等数学（多元/级数，非极限）。
- **经验**：先验证关键假设（key 可用、LaTeX 可用）再大规模开发。

### 轮次 3：构建双引擎流水线（开发）
- **任务**：在 starter 基础上新增高等数学求解能力 + DeepSeek 迁移。
- **AI 用法**：设计 `llm_solver.py`（DeepSeek 客户端）与 `solve_advanced.py`（SymPy 多元/级数求解器）；把 LLM 调用抽象成单一模块，便于切换任意国产模型。
- **Prompt 设计（对 DeepSeek）**：要求"分步推导、每行一步、最后以'答案：'开头、公式用 $...$"——用结构化约束提升输出可解析性。
- **产出**：`domain_skills/advanced_math.yaml` + 扩展求解器。

### 轮次 4：首次端到端测试（验证）
- **任务**：用拟好的高等数学作业跑通流水线。
- **结果**：11/11 全部求解，但暴露 **3 个问题**：
  1. 题 7（$\sum\frac1{n^2}$）被误判为"发散"（应为收敛）；
  2. 题号带 `PartA` 前缀（作业标题用了 `Part X`）；
  3. DeepSeek 证明步骤含 `$$...$$` 多行公式，影响排版。
- **经验**：跑通 ≠ 正确，必须逐题核验答案。

### 轮次 5：修复判敛错误（Debug）
- **问题根因**：`solve_p_series` 解析 $1/n^2=n^{-2}$ 时取了 `exp=-2` 作为 p 值，`-2>1` 为假 → 误判发散。
- **修复**：p 值取 `-exp`（因为 $1/n^p=n^{-p}$）；改写分支逻辑并补 `1/n`、$n^{-1/2}$ 特判。
- **AI 用法**：用 SymPy 反查 $n^{-2}$ 的 `exp` 属性，定位符号解析偏差。

### 轮次 6：规范化作业格式 + LLM 输出（打磨）
- **修复**：
  - 作业标题去掉 `Part X` 前缀，使题号为纯数字 1-11；
  - `llm_solver` 增加后处理：把多行 `$$...$$` 折叠为单行 `$...$`。
- **经验**：LLM 自由输出要过一层"格式规范化"才能进排版。

### 轮次 7：PDF 渲染审阅（质检）
- **任务**：渲染生成的 PDF，逐页检查排版。
- **发现**：题 7/8 步骤里出现 `**收敛**|**`——因为步骤字符串里用了 Markdown 加粗 `**`，LaTeX 不识别。
- **修复**：把步骤里的 `**...**` 换成 `\textbf{...}`（LaTeX 加粗）。
- **经验**：交付物必须在"用户真正看到的层"（PDF 渲染）验证，不能只看 JSON。

### 轮次 8：终验（完成）
- **重跑**：11/11 全部正确，PDF（xelatex + ctex 中文）编译成功，排版规范。
- **结果**：高等数学域外求解率从 Claude 基线 40% 提升到 **100%**。

## 关键 Prompt 摘录（DeepSeek 证明题）

```
请用简体中文求解下面这道证明题，并满足：
1. 给出完整、清晰的分步推导过程，每行一步，用序号标注；
2. 最后一行以"答案："开头，给出明确的最终答案；
3. 所有数学公式用 LaTeX 行内符号 $...$ 表示。
```

设计意图：**结构化输出约束**（分步 + 固定结尾 + LaTeX 公式）让 LLM 输出可直接被 pipeline 解析，这是"LLM 进工业流程"的关键。

## 失败经验总结

1. **符号解析陷阱**：SymPy 的 `n**-2` 与数学直觉 $1/n^2$ 的指数符号相反，直接取 `exp` 会判错——必须理解库的表示再映射到数学语义。
2. **跑通不等于正确**：首次 11/11 全"解出"，但答案有错（题 7）。自动求解必须逐题核验标准答案。
3. **LLM 输出要规范化**：DeepSeek 的多行公式、Markdown 加粗都不能直接进 LaTeX，需一层清洗/折叠。
4. **交付物看渲染层**：JSON 里数据对，PDF 里可能渲染错（`**收敛**`）。要用用户看到的产物验收。

---

## 工作流设计与复用价值

- **规则 → SymPy → DeepSeek 三层递进**：先规则识别题型，能精确算的用 SymPy，算不了的推理交给 LLM。这套模式可复用到任何学科。
- **LLM 单点抽象**：`llm_solver.py` 一个模块封装 API，切 Qwen/Kimi/DeepSeek 只改一处——这是"跨平台迁移"的工程范式。
- **领域知识驱动**：新增学科只需加 YAML 领域文件 + 求解函数，无需改主流程（ontology-grounded）。
